# Daylight Master Design v1.1 audit

Compared the implementation with the supplied **v3-Productivity App.pdf**, the 16-page Daylight Master Design Specification dated November 6, 2026. The plan labels some mechanics as proposed and leaves several product decisions open.

| Requirement                                         | Current implementation                                                                                                                                                                                                                                                                                                                                                        |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Planner and navigation (§§1–2)                      | Separate work areas, quick capture, compact suggestions, a secondary backlog, and Day, Week, Month, and 12-month views.                                                                                                                                                                                                                                                       |
| Fixed routines (§3, example A)                      | Fixed weekday and time blocks affect capacity. Pause, skip, move, and occurrence outcomes are supported. Google export uses a recurring event with exceptions. Live synchronization remains a separate check.                                                                                                                                                                 |
| Tasks, deadlines, and sessions (§4, examples B–C)   | Tasks and deadlines can be created independently and linked. Deadline markers are separate from work sessions. Sessions have independent outcomes, and completing the task preserves work history. The Deadlines view includes approved milestones. Standalone deadlines lack AI decomposition.                                                                               |
| Milestone planning (§5)                             | Project setup, workload and budget fields, AI drafts, dependency validation, and explicit approval exist. Current-milestone task drafts lack proposed sub-deadlines. Slipping approved milestones lack an explicit revision and approval workflow. Capacity-aware output quality needs evaluation.                                                                            |
| Daily planning and evidence (§§6–9, examples D–F)   | Daylight calculates available minutes and shortfalls, preserves unknown actual time, and distinguishes focus self-report from evidence. Saved reviews feed planning. Daily priorities use a manual AI refresh. Review offers short optional fields and flags a missing blocker, but does not select only the questions that could change the assessment before generating it. |
| AI implementation (§10)                             | Structured inputs, deterministic calculations, response validation, prompt versions, saved snapshots, and user approval are in place. Live model quality and repeatability across representative cases remain unverified.                                                                                                                                                     |
| Reporting (§11)                                     | Daily reviews and a seven-day summary exist. The daily report has one pacing status. Per-project pacing reasons within the report, upcoming work in the weekly summary, and recurring bottlenecks are incomplete. Weekly delivery remains an open decision.                                                                                                                   |
| Future Self reflection and existing rules (§§12–14) | Reflection remains external. The planner uses manual scheduling and user estimates, with no required behavioral regimen.                                                                                                                                                                                                                                                      |
| Technical direction (§§15–16)                       | Next.js source, Supabase persistence, and Google Calendar integration exist. The local sync fix has automated coverage. The Vercel site still served the legacy deletion dialog when inspected, and the updated integration awaits a signed-in round trip.                                                                                                                    |

The calendar is a shared schedule for the selected writable Google calendar and optional holiday subscriptions. The planner can reflect a Google change while retaining the original Daylight task, deadline, or evidence. Multiple writable calendars and full Google event editing remain outside the current implementation.
